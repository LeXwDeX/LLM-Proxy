# LLMs Proxy

English | [简体中文](README.zh-CN.md)

LLMs Proxy is a Go HTTP service that gives clients a single model API entry point and forwards requests to configured upstream providers. It supports client authentication, model alias mapping, target routing, usage recording, cost accounting, and a web admin console.

Source repository: <https://github.com/LeXwDeX/LLM-Proxy>. Development constraints are described in [`AGENTS.md`](AGENTS.md) (Chinese).

## Feature Overview

- Upstream types `azure_openai`, `openai`, `claude`, `gemini`, `openai_image`, and `dual_protocol`.
- DeepSeek, Alibaba Cloud Bailian (百炼), and legacy type aliases map to `dual_protocol`; the canonical type list is defined in [`internal/config/endpoint_type.go`](internal/config/endpoint_type.go).
- OpenAI-style `/v1/*` proxy entry point, local model list, admin API, and web UI (the admin console is currently in Simplified Chinese; UI labels in this README include the original Chinese text).
- Embedded persistence based on bbolt; no separate database installation required.
- Usage is costed from the configured official API rates, model group multipliers, and usage records.

### Quota Plan Sync

The "Batch operations" (「批量操作」) action in quota management can sync a plan to selected clients, an entire project group, or an entire job level. Each sync reads the source client's plan, resolves the target list, and overwrites the whole batch within a single database transaction; if any validation or write fails, the whole batch is rolled back. Combined selection criteria are unioned and the source client itself is excluded. On success, the actual list of synced clients is returned and their quota status is refreshed.

What gets overwritten is the complete model group selection plus each group's personal quota multiplier, including blank values, explicit `0`, and positive numbers. Extra model groups that the target previously had are removed, and an empty source plan clears the target's plan. Targets keep their own job-level binding, and daily/weekly/monthly available quota is still computed as "model group base × target's job-level multiplier × personal multiplier"; identity, keys, authorization, and historical usage keep their original values. Independent edits made after a sync are separate subsequent operations; no ongoing relationship that follows the source client is created.

A client's quota is granted only by the model groups in its plan: a request whose selected target and upstream model match no binding of any plan group (including every request from a client whose plan is empty) is rejected before forwarding with `403` `quota_not_configured` (no `resets_at`; client-level rejections such as `accounting_unavailable` take precedence), and there is no built-in unlimited fallback group, so free or unlimited access has to be configured explicitly, for example with a coefficient of `0`. Binding changes take effect when the background quota refresh finishes, so a route that was just granted (for example by a model group edit or a target rename) can briefly be rejected.

### Raw Usage Client Index

For legacy v1 data without independent raw-owner evidence, a completion marker, a cursor, or v2 progress, cost reads can use the raw fallback only after checking any existing client/hour counts, digests, and index pointers against the complete raw hour. This read-only compatibility path does not certify migration or create proof. Mixed legacy and v2 hourly cells are combined by logical dimensions before integrity comparison; ambiguous legacy dimensions remain errors.

After startup, a derived `usage_events_by_client_v1` index is built in the background in batches; the HTTP service does not wait for the migration to finish before starting. The v2 build keeps its progress and required-version marker in `usage_client_index_progress_v2` and `usage_client_index_required_v2`, and per-event proofs in `usage_client_index_proofs_v2`. It covers retained raw usage events and leaves raw event keys, hourly rollups, and the cost formula unchanged; exact-cost reads use the index and proofs as evidence, not as a substitute for raw/rollup reconciliation. New events (including recovery-journal replays) are updated together with the index and both hourly rollups in the same transaction; retention cleanup deletes index entries at the same time, while long-term hourly rollups and the proofs are kept.

The migration commits each batch together with its v2 progress and proof, and resumes from the latest committed proof after an interruption. Existing v1 index rows are accepted only when an independent raw owner and the legacy hour counts and digests prove them; a completed v1 index stays readable under legacy verification, while partial v1 progress is rejected as ambiguous. Before completing, it verifies in batches that raw records and the index correspond in both directions, then verifies revision numbers, counts, and checksums per client/hour segment. Each segment is verified within a single read transaction, so the global revision no longer has to stay unchanged for the whole scan; normal ongoing writes do not force a full re-verification. Segment revision conflicts are retried at most three times. The completion marker is written only after verification succeeds; the record count in that marker is the sum across segments at the time each was verified and does not represent a whole-database snapshot at a single point in time. Background migration failures are logged and retried with exponential backoff starting at 1 second, with a maximum interval of 1 minute, without waiting for the next startup. On shutdown, the process cancels the migration and waits for it to exit before closing the database. Initialization performs one write transaction per batch and verifies the completed index in both directions in bounded batches; these costs grow with retained history, and this description makes no throughput promise.

When retention cleanup encounters a raw event that cannot be decoded, it moves the original key, original bytes, quarantine time, and diagnostic reason into `usage_events_quarantine_v1`, then removes it from the raw event bucket; other expired records continue to be cleaned up and permanent rollups are unchanged. Quarantine and removal happen in the same transaction, and a WARN is logged without the event body. When ownership cannot be determined, a globally conservative failure applies: the unresolved quarantine is recorded, the legacy completion marker is removed, and completion verification is withheld while the quarantine exists. The v2 progress, required-version marker, and proof bucket are retained; quarantine does not delete them. Exact-cost reads that depend on the index fail closed when the available raw/index evidence is corrupt or its scope cannot be proven; they do not treat that evidence as zero. Quarantine keeps the original bytes for review; unresolved malformed evidence is attributed from any surviving original proof, and a missing or invalid proof keeps the affected scope unproven. With v2 progress present, retention checks each decoded event's index proof before pruning it; an invalid proof rejects the current batch, and the call returns the count from earlier committed batches. Quarantine evidence is never deleted automatically; the corrupted history must be investigated and handled, and must not be treated as zero usage. Recovery-journal replays for a quarantined original key also return an error and are left pending, to avoid double-counting into permanent rollups.

Retention cleanup writes a versioned SHA-256 digest receipt for each decodable identity in the same transaction that removes its raw row and client-index entry; the event payload is not retained. Receipts are append-only with no garbage collection, so disk usage grows O(N) with retained identities. An explicit `RecordID` must carry a non-zero timestamp and is rejected before a default timestamp can be assigned. Retry identity comparison hashes the normalized event and excludes only the derived `PricingRuleID` and `PricingRuleVersion`; every other field, including pricing context, diagnostics, and cost completeness, remains part of the digest. Until both receipt-migration markers exist, initialization compares retained raw counts with permanent rollup counts and aggregate evidence and establishes a conservative `legacy_unknown_before` watermark at the end of the newest untrusted hour when untrusted evidence exists. Hourly cells that cannot be decoded, and aggregate keys with an invalid segment count or hour (v1.0.1 readers skipped both), do not stop this step, and every such key is logged at ERROR with its bucket and key but never the cell value. Retention is the only path that deletes raw rows; it always removes a complete prefix below its cutoff and quarantines undecodable rows only inside that prefix. The scan treats every recognizable corrupt hour as untrusted, including a current or future hour: an older raw row may arrive after the scan, so the earliest surviving record cannot prove that the hour was never cleaned. A key that names no recognizable hour cannot bound any identity; it is logged and persisted as an unknown-range marker. The `legacy_unknown_before` watermark stays capped at the start of the scan hour, but admission also enforces a separately persisted, uncapped untrusted-through boundary. Untrusted evidence in the current or a future hour therefore rejects new identities below that boundary, including writes in that hour and later hours. The unknown-range marker rejects every new usage identity and is sticky: no code in this version clears it. The scan result is cached per process; if the step itself fails (for example a missing bucket or an I/O error), every new usage identity stays blocked and the step is retried with exponential backoff (1 second up to 1 minute) instead of rescanning on each write. Any write below the enforced boundary with neither raw data nor a receipt is rejected with `ErrUsageIdentityUnverified`; when it comes from recovery-journal replay it is moved to the rejected sidecar described below. Permanent rollups are not rebuilt automatically.

The storage interface `ReadClientEvents` reads retained events within `[from, to)` by client and UTC hour. Each event-reading transaction has a batch limit and is re-checked against the hourly revision number maintained within the transaction; if the hour changes, it retries at most three times. When the index is incomplete or cannot stabilize, it returns an explicit error rather than partial results. Different hours may come from different snapshots. A single-segment verification during migration reads the client's entire hour, so the transaction length depends on the segment's record count. This interface is not proof of a complete ledger for history that has been cleaned up; pricing callers must still reconcile raw history against permanent hourly rollups.

Recovery-journal replay moves a row to the private `<journal>.rejected` sidecar (mode 0600, like `.corrupt`) only when the ledger rejects it permanently: its identity falls below the enforced receipt boundary (`identity_unverified`), its digest conflicts with an already committed row or receipt (`digest_conflict`), or the bundle fails validation or is only partly committed (`invalid_bundle`). Each sidecar line is a JSON object with `rejected_at`, `reason`, `error`, `record_id`, `client`, and `line`, which holds the original journal line's raw bytes encoded as base64, so lines that are not valid UTF-8 are kept unchanged. The entry is written and synced before the row leaves the journal, and the sidecar never holds the same raw bytes twice (deduplicated by SHA-256), even while a failing journal rewrite re-rejects the line on every retry. A completed move is logged at ERROR; if the sidecar copy was saved but the journal rewrite failed, a different ERROR says the line is still pending. Rejection never charges or counts the row automatically, but it does not prove that the row was never committed: `identity_unverified` cannot distinguish a pruned committed row from a first arrival, and a partially committed bundle may already have charged rows. Before the row leaves the journal it is registered as unresolved evidence. Unresolved `identity_unverified` and `invalid_bundle` evidence, including evidence re-registered from an existing sidecar at startup, keeps scoped cost and quota calibration for the affected client blocked with `ErrUsageHistoryIncomplete` while accounting completeness is unproven; a recheck can resolve that single evidence only when the saved bundle identity and accounting completeness are both proven in the same transaction; an identity-only result does not resolve it, and the recheck never creates or backfills raw rows, rollups, or charges. A `digest_conflict` is treated as resolved only when every bundle identity is verified as committed and accounting completeness is proven, because identity evidence alone cannot prove that both billing rollups survived. Transient failures (I/O, a closed or failed bbolt transaction, a missing bucket, a quarantined identity) keep the row in the journal and calibration fails closed. Nothing replays the sidecar automatically. Manual review: back up the full set first; decode each original line on an offline copy, for example `jq -r '.line' <journal>.rejected | head -n 1 | base64 --decode` for the first entry (do not use jq's `@base64d`, which replaces invalid UTF-8); compare each decoded line with the committed raw row, receipt, and both rollups for the same timestamp and `RecordID`; decide whether the usage is already billed, is a duplicate, or is genuinely missing; and only bill missing usage through a reviewed maintenance procedure, never by appending the line back to the journal unchanged.

Manual review order for quarantine evidence: first save a consistent backup that includes the database, recovery journal, and migration snapshots; on an offline copy, check the quarantined original key/original bytes, both permanent rollups, and the state of the same event in the journal; confirm ownership, how the raw event should be restored, and whether its cost has already been accumulated, to avoid calling `Record` again on an already-aggregated event. **There is currently no supported admin release interface or general offline repair tool**, so this version does not offer a "delete the quarantine record to release it" operation. The admin API can list usage review evidence with its resolved state (`GET /admin/data/usage/unresolved`) and recheck one entry (`POST /admin/data/usage/recheck`). It reports `accounting_verified` when identity and accounting proof both hold, and `accounting_restored` only when that proof changes one previously unresolved entry to resolved. Reusing an operation ID returns that operation's stored result and does not re-evaluate current evidence; to determine current state, read the latest evidence and run a new recheck with a new operation ID. It does not create or backfill raw rows, rollups, or charges, and it does not apply to quarantine evidence. Releasing requires a dedicated, reviewed maintenance program that repairs raw records, the index, and rollups in the same write transaction, handling quarantine evidence one entry at a time; only after everything has been verified may it clear the `usage_events_quarantine_count_v1` unresolved marker, invalidate the old completion marker and migration cursor, and rerun full migration verification. Clearing only the completion marker, deleting only the quarantine bucket, or only replaying the journal cannot prove the ledger is consistent. Until review is complete, keep the evidence and markers, use the fallback path described below, and do not treat quarantined events as zero consumption. The v2 progress, required-version marker, and proof bucket are part of that evidence and must stay with the snapshots; this version has no supported admin or offline procedure to repair or clear v2 proofs, so deleting v2 markers is not a release or repair step.

An offline reindex maintains the derived index but does not recertify accounting: existing proofs are retained, and changed raw bytes can still block pricing and retention.

### Exact Historical Cost and Quota Calibration

`ReadCostUnits` keeps a target/model whose price is stable within the hour as an hourly unit. When a pricing-template override, a minute-level time slot, or a timezone offset changes the price within a UTC hour, or when request-conditional pricing exists, it uses the event's target, model, timestamp, and pricing context to select `pricing.Resolver` rates, and the cost formula is still `usage.CostRates.CostFor`. The target template, global template, catalog price, and provider isolation rules are unchanged. The storage layer uses the resolver passed in by the caller; admin reports and quota each apply the model group multiplier only once. `ReadCostUnits` performs its database reads, including raw, rollup, owner, unresolved-evidence, and applicable index-evidence checks, in one read transaction; rate selection and cost calculation run after that transaction closes.

Single-client quota calibration first drains only this client's queued journal rows from the start of the calibration window onward, then reads the union of the daily/weekly/monthly windows only once (an ISO week may start before the beginning of the month) and assigns each priced unit to the three windows. When the read is client-filtered and a window classification is available, quota calibration enumerates only that client's indexed rows and quota cells for the requested hours; the scope is used only after a probe proves the enumeration complete for the window, and every shape the probe cannot prove falls back to the full scan and counts one `client_scope_fallback` fallback. A scoped read that still fails after the probe accepted the scope discards its partial result and replays the read without a scope; the replay is authoritative and also counts one `client_scope_fallback` fallback. The scoped drain is a prerequisite, not proof of completeness; the authoritative read must still prove it. Minute-level templates use the client index plus a bounded independent scan of raw evidence; that scan can decode other clients' rows, but it excludes them from the result. The last read transaction for each hour re-checks both the hourly revision state and the record count in the permanent rollup (`record_count`, falling back to `Requests` for legacy cells). When the index is incomplete, there is an unresolved quarantine, or the evidence is inconsistent, diagnostics are recorded, all partial results are discarded, and the read falls back to the full raw-event scan. That fallback is still guarded by raw/rollup and proof checks; it does not treat unresolved or unprovable evidence as zero. Corrupted or unknown-scope evidence can extend the block to a broader client/model scope; a valid owner can prove that a disjoint scope is unaffected. Unresolved usage evidence from a rejected or invalid record is different: scoped cost and quota reads fail with `ErrUsageHistoryIncomplete` instead of falling back. The full path still skips events that cannot be decoded, and the bidirectional raw/rollup record-count check makes the affected client fail explicitly. Supplementary records count toward this check but do not add requests. When raw events that require exact pricing have already been removed by retention cleanup, an error is returned; it must not guess an hourly price or successfully return an understated amount. History with stable prices can still use permanent rollups.

Multi-client reports scan raw history once within one read transaction and reuse the same set of cost results for totals, time buckets, clients, models, model groups, and target/model breakdowns. Summary's exact last_hour shares this scan with the other windows; when all prices are stable, only last_hour raw events are scanned. Reports keep the existing hourly window attribution and each entry point's request-count basis (all requests or successful requests), changing only the price-selection moment to the actual event time.

Admission, cold-client `Status`, and failed-calibration retries from the `RecordUsage` completion path share per-client single-flight coordination (one calibration with concurrent callers waiting for it) and a 10-second failure backoff. During backoff, they do not repeat Drain/Evaluate; existing counters are retained and admission is denied until reliable calibration succeeds. Once retry is due, calibration still runs synchronously and concurrent callers wait; this is not a no-delay completion guarantee. For bundle price checks, a nil resolver only avoids adding `missing_iteration_price`; it does not prove pricing is complete or disable other price and partition checks.

Stable-price rollups retain price-check coverage counts. If a real resolver no longer finds a price for a billable supplementary or fallback row, reports preserve the known cost and add a query-only incomplete-cost count, without double-counting rows already incomplete. `incomplete_cost_count` counts records, not requests: a request whose fallback attempt produced no output stores two records and can contribute 2. Explicit zero prices remain valid, non-billable rows are excluded, and restored prices remove only the query-derived marker. Legacy or mixed cells without full coverage metadata contribute a conservative marker when a price is missing and billable tokens remain; this is not an exact per-record count. These checks do not rescan all raw history and continue after retention cleanup.

The index, hourly revision state, quarantine records, usage receipts, receipt watermark/meta markers, unresolved usage evidence, usage recheck receipts, aggregate source-loss markers, aggregate backfill snapshots, v2 index progress/required/proofs, the odd-row proof index (`usage_proof_odd_v1`), raw owners, and migration markers all live in the same bbolt file and are preserved by consistent backups of the database. After restoring a backup that already has markers and cursors, the migration keeps a completed v1 build under legacy verification or continues an unfinished v2 build from its latest committed proof; an old backup without an index can build the derived index from raw records. If all three v2 anchors are absent, the database cannot distinguish a never-enabled v2 build from a lost one, so this state is not proof of a completed v2 build. A v1 source-loss rebuild does not certify v2: it keeps the source-loss marker and existing v2 anchors, and exact accounting can remain blocked. If an initialized aggregate bucket is missing when the database opens, a persistent `usage_aggregate_source_missing_v1:<bucket>` marker records it. A missing quota aggregate blocks cost-unit reads, and accounting proof rejects either marker; no code clears these markers. The usage recovery journal is a separate file; include it with its `.corrupt` and `.rejected` sidecars, configuration, and existing migration snapshots in the same backup set. After restore, it is replayed through the idempotent `Record` path. Never overwrite data produced by a new instance with an old backup.

Windowed integrity reads. The integrity checks behind quota calibration (`ReadQuotaCostUnits`), cost reads, Summary, and the aggregate reports used to walk every raw row, raw owner, receipt, quota cell, rollup proof, fresh attestation, and client-index entry on each read. When an in-memory classification is available they walk only the keys of the requested UTC hours plus a bounded set of anomalous objects: any object whose verdict could depend on something other than its own key hour, for example a non-canonical or unparseable key, a row whose event time or index proof points to another hour, an invalid owner, a row that does not decode, or an index entry whose attribution needs the whole index. Unresolved evidence and quarantine are always checked exhaustively. The verdict (success, error class, and returned data) is the same as the exhaustive checks; a differential test suite and a forced-fast run of the `nosql` and `quota` tests (`make test-fast-integrity`, also a CI step) check this. The classification is held only in memory and is not persisted. The proxy builds it in the background after startup migrations, the proof-cache warm-up, and journal replay, and then every 5 minutes (`USAGE_INTEGRITY_CLASSIFICATION_INTERVAL_SECONDS`, a positive number of seconds). Until a build completes, when more than 10,000 anomalous objects exist, and from the start of any maintenance write in this process (retention, quarantine, receipt migration, backfill, index migration or rebuild, reindex, data migrations, or a realtime row that is itself anomalous) until the next completed build, reads use the exhaustive checks. Unresolved registration and rechecks write only evidence that is always checked exhaustively and keep the classification. `GET /admin/metrics` reports `usage_integrity`: `complete`, `epoch`, `anomalous_count`, `last_duration_ms`, `fast_reads`, `fallback_reads` per reason (`incomplete`, `epoch_changed`, `index_progress_changed`, `anomalous_overflow`, `partial_refs_fallback`, `client_scope_fallback`), `inflight_writers`, `classification_stalled`, `discarded_rounds`, `last_discard_reason`, `segment_max_tx_ms` and `writer_lock_max_ms`; it contains no keys or stored bytes. A build is split into short read transactions with a per-segment budget (2048 objects or 50ms); an interrupted round is retried in the same call from the saved cursor, while cancellation or a process restart starts the next round from the beginning. Only `epoch_changed` or `index_progress_changed` discards extend the consecutive discard streak; three such discards set `classification_stalled`; the waits after successive discards are 5s, 15s and 45s, after which the loop returns to the configured interval. The two max metrics are process-lifetime maxima. Maintenance tools that open the database must run while the proxy is stopped (bbolt's file lock is advisory). A writer that bypasses this process, for example one ignoring the lock, can add an anomalous object outside a read window that the fast path does not see until the next classification completes (at most one interval plus about two builds); the exhaustive checks would report it on the next read. This is the only detection difference.

Persistent odd-row proof index. Accounting proofs no longer classify every raw row and receipt by scanning whole buckets inside each write batch, and, once the index is ready, startup no longer decodes every raw row to warm the cache. A persistent index (`usage_proof_odd_v1`, in the same bbolt file) records only the objects a key-prefix walk cannot reach: raw rows whose key is not `usageKey(event)`, and receipts whose key stamp is not canonical UTC. Entries are located by key-stamp UTC hour; entries that cannot be located by hour — unparseable stamps, rows that may overlap every hour, rows with a readable raw owner, and rows whose raw owner cannot be read — are global and loaded by every proof, so proof cost grows with that odd history instead of the whole history. Canonical rows and receipts are never indexed. A start-up migration under a two-minute budget builds or resumes the index before the proof-cache warm-up; if it cannot finish, startup continues, the warm-up falls back to decoding every raw row, proofs keep the full-scan fallback, and the next start resumes from the stored cursor. Supported writes maintain the index and advance the revision an interrupted build is bound to, so a large build converges across starts; a writer that advances the revision without maintaining the index forces a rebuild. A completed index is trusted only while its classification scheme matches and no writer that advances the raw revision without maintaining the index has run since the build; the revision is a writer sequence number, not a digest of the data, so it detects an older binary or out-of-band edit that bumps it, not a same-revision rewrite. A mismatch discards and rebuilds the index, and a build interrupted between its raw and receipt phases is discarded when the raw revision moved instead of stamping a revision it never observed. Every supported writer maintains the index in its own transaction; out-of-band edits and restored data require the Go-only reset and migration entry points. Damage the index can determine from its own checkable state — a missing or unreadable bucket or marker, a foreign scheme or revision, a leftover phase marker, a per-kind count or pointer that disagrees with the entries, an entry digest that no longer matches its object, or an unreadable raw-owner source — makes proofs fall back to the exhaustive scans; it never fails open on that account. That guarantee is bounded by the index's own checkable state. The index cannot detect every out-of-band change. Examples include: an odd object added out of band that the index does not record, including an insertion behind a resumed raw cursor; a location entry and its per-kind count removed together in a self-consistent way while the other pointer and entry checks stay self-consistent (its pointer may remain); and a readable owner added or rewritten outside the supported writers (see the owner residual risk below). A restore that provides only the raw or receipt buckets, a restore into a different database, or any other partial restore may delete or rewrite objects the index still references, which the entry, pointer, and count checks can detect, but the restore as a whole is outside this guarantee because it can also add odd objects the index does not record; after any such restore, run `ResetUsageProofOddIndex` followed by `MigrateUsageProofOddIndex` before serving. `GET /admin/metrics` reports `usage_proof_index`: `ready` says whether proofs currently trust the persisted index's own state, not that the index is consistent with the data, and the process-lifetime counters `full_classifications` and `index_loads` count keys examined by the fallback full classification scan and entries loaded from the index; it contains no keys or stored bytes. A runtime `ready:false` means proofs are scanning the whole history through the fallback. An owner rewritten outside the supported writers is outside this guarantee and requires the reset and migration entry points.

Usage retention observability. `GET /admin/metrics` also reports `usage_retention`, a read-only snapshot cached for about five minutes (the first read returns `available:false` with `reason:not_ready` while the refresh runs in the background). It contains no keys, client or model names, or stored bytes. `buckets` reports `present`, `entries`, `pages`, and `in_use_bytes` for the `receipts`, `receipt_owners`, `raw_owners`, and `fresh_attestations` ledgers; `events` reports the earliest and latest canonical UTC `usage_events` key stamp (one that round-trips through RFC3339Nano in UTC) and `invalid_boundary_keys`; keys carrying a timezone offset do not round-trip, so they never define an endpoint and are counted in `invalid_boundary_keys` when the boundary inspection reaches them; each boundary second is scanned because RFC3339Nano key order is not time order within a second, and `invalid_boundary_keys` counts only the boundary keys actually inspected while locating those endpoints: the invalid prefix before the first canonical key, the invalid suffix after the last, and invalid keys inside the earliest and latest boundary seconds; invalid keys strictly inside middle seconds are not counted; `metadata` reports the `legacy_unknown_before` and `untrusted_through` receipt watermarks (corrupt values set `legacy_unknown_before_invalid` or `untrusted_through_invalid` instead of being echoed), the `watermark_done_v1` and `watermark_done_v2` markers, and `unknown_aggregate_hour`; `captured_at` dates the snapshot. Until the first refresh publishes a snapshot, reads return `available:false` with `reason:not_ready` while that refresh runs in the background. The snapshot reports `store_unavailable` when the store or its database is unavailable; otherwise a failed refresh reports `transaction_failed` for a failed read transaction or `internal_error` after a recovered panic. A failed refresh replaces the previous successful snapshot for one refresh interval, so the endpoint degrades to `available:false` instead of serving values it could not refresh.

### Unreleased Bundle Ledger Compatibility and Rollback Limits

New hourly usage cells use versioned keys with hex-encoded dimensions. Existing cells are not rewritten; readers scan both formats in one transaction. Total request counts include structurally valid legacy cells even when their dimensions contain ambiguous separators. Dimension-based legacy readers return an error for such keys instead of silently omitting them. Like v1.0.1, the overview request total (`Count`) skips malformed keys and undecodable cells and logs at most one WARN per minute with the skipped count, the first skipped key, and the number of suppressed warnings; dimension, billing, and quota readers still fail on them. Old four/five-part keys retain their historical interpretation; lost attribution cannot be reconstructed from pruned raw data. Receipt migration checks the combined legacy/versioned record counts, exact versioned lower bounds, and the separate quota index. Older binaries do not understand the new keys and are not safe in-place downgrade artifacts, even if a narrower data-contract test passes.

The unreleased bundle ledger stores a root and linked supplementary records, independent pricing evidence, non-billable token subsets, and rollup record counts. **No older version can be rolled back to in place once this version (with the versioned hourly keys introduced with the bundle ledger) has written data.** v1.0.1 (`0e7ebfd`) does not preserve the bundle contract and can overcharge or return `ErrUsageHistoryIncomplete`. Commit `b36b5445853c33ee0b804de46d42f6d8a1b152fa` is only a pinned data-contract test target: it replays journals, reads raw rows, and prices bundles, but its `Count`, `Aggregate`, and `SumByClientRange` cannot parse versioned cells and silently report zero for them without an error, so overview totals, usage reports, and the legacy quota fallback would lose that usage. It is not a released or production-safe rollback artifact, it does not understand receipts or meta markers, and its other known bugs still need to be addressed. The integration test asserts the b36b544 aggregate-reader gap as a counterexample.

A rollback is therefore only possible by restoring the complete, consistent backup set taken before the upgrade, together with the binary that wrote it, and discarding every write the new instance made. First confirm that this data may be discarded; otherwise do not roll back.

1. Stop new writes and drain in-flight requests and queued writes.
2. Preserve the current consistent set (database, recovery journal, its `.corrupt` and `.rejected` sidecars, configuration, and migration snapshots) as evidence, separately from the restore.
3. Confirm the new instance's writes may be discarded, then restore the pre-upgrade set as a whole: database, recovery journal and sidecars, configuration, and migration snapshots. Never restore only some of these files.
4. On an isolated copy, reconcile records, request counts, tokens, costs, and pending, quarantined, and rejected journal entries before admitting traffic. Replay identity is the stored timestamp plus `RecordID`; both must stay stable. A `RecordID` alone does not deduplicate across different timestamps. A healthy HTTP endpoint does not prove replay succeeded.

Do not clear journals by hand, overwrite new accounting data with an old database, or combine an old database with the current journal. The [cross-version integration test](test/integration/usage_bundle_rollback_test.go) checks stable, exact, and conditional pricing, replay idempotency, continued writes, and the aggregate readers against pinned versions, including the b36b544 counterexample above; it is not production deployment acceptance.

## Requirements

- The Go version is defined in [`go.mod`](go.mod) (currently declares Go 1.27.2).
- Docker/Compose is only needed for container deployments.
- Upstream API credentials and client access keys should be injected via protected local configuration or the environment; do not commit them to Git.

```sh
./bin/llms-proxy -config config/config.json
```

`make build` tries to update the built-in model catalog from models.dev; if the network is unavailable, the existing catalog data is kept. The program reads `config/config.json` by default, and `-config` can specify another file. If the configuration does not set a listen address, it listens on `0.0.0.0:8000` by default; the `SERVER_BIND` environment variable can override the listen address.

After startup, check health:

```sh
curl -fsS http://127.0.0.1:8000/healthz
```

Clients call the proxy via `/v1/*`. Alias matching rules in model mappings differ from the model name sent upstream: the upstream model name is sent exactly as configured, including case. The API proxy is primarily pass-through; clients should use the protocols, paths, and request formats that the upstream supports.

### Model Prefix and Shared Pricing

The "Model prefix" (「模型前缀」) field on the target edit page corresponds to `model_prefix`. The full outbound model name is the prefix directly concatenated with each row's upstream model value, e.g. `Vendor/` + `fable5` → `Vendor/fable5`; case is preserved, no separator is added automatically, and leaving it blank keeps the original behavior. Clients still use the original alias, and the allowed scope and billing model identity are unchanged. HTTP JSON, multipart, requests with the model in the path, Responses WS, and model checks all use the same outbound rule; when switching targets, the name is rebuilt from the original request. Model names in upstream responses are still passed through unchanged.

Model pricing supports selecting multiple targets and models at once; for example, `fable5` and `fable5-1` on two channels can share one set of base prices, cache prices, and time-of-day rules. On save, every selected target × model combination is validated, and each specific target must already have that model configured; the default global fallback is selected separately. Duplicate fallback prices or overlapping effective periods for intersecting combinations cause the whole submission to be rejected. Costs are still computed separately by the actual target, model, and event time, and the multiplier and quota rules are unchanged.

The admin API `/admin/data/pricing-templates` adds `targets` and `models` arrays; a shared rule has a single ID. The legacy `target` and `model` fields and existing data remain compatible; the returned legacy fields represent the first item, and the arrays define the full scope. When editing a rule, its binding set is fixed, and changing the price applies to the entire rule; to change bindings, copy the rule and schedule an effective time, keeping the original rule. Historical costs continue to select prices by the original event time; directly editing a price inside an old effective window still affects recalculation for that window. The legacy single-model interface cannot overwrite or delete multi-binding rules.

A deployment pool's `name` is still a lowercase internal identifier; the new `display_name` preserves the case entered by the user. The admin page can correct the displayed case, while member targets and client authorization references stay unchanged. Old data did not store the original case, so the display falls back to `name`, and it can be re-entered on the edit page; names that differ only in case cannot be created as two pools.

### Target Rename and Merge

Renaming or merging targets must go through `POST /admin/data/targets/{name}/rename` with body `{"new_name": "...", "merge": false}`; do not edit bbolt offline. Usage events and the usage/quota hourly aggregations are keyed by the target name at write time, and the endpoint never rewrites or deletes them. Instead, one bbolt transaction updates every name-bound object:

- Rename (`merge: false`, the new name must not exist): the target record and its order are renamed; every pricing template bound to the old name also binds the new name, and every model-group binding of the old name gets a copy for the new name. The old name is kept in both, so history keeps its target template and model group while new traffic uses the same ones. Rejected with 409 if the new name already has usage history (for example from a deleted target), if the extended bindings overlap another template's effective period, or if a model-group binding would belong to two groups.
- Merge (`merge: true`, the new name must exist): the source target is deleted; the destination's configuration and bindings are unchanged, and the source's pricing templates and model-group bindings are kept for its history.
- In both cases each client's `allowed_targets` replaces the old name with the new name, so a list never becomes empty (which would mean "allow all").

`If-Match` takes the source target ETag. The response lists the synced `pricing_templates`, `model_groups` and `clients`, plus the new `etag`; the audit log records `rename_target` or `merge_target` with the same detail, and quota counters are refreshed. Runtime key-pool and breaker state starts fresh under the new name. Removing the old name from a pricing template or model group, or deleting its aggregation cells, makes history fall back to global or catalog prices or makes accounting fail closed (503), so keep retired names in their bindings.

### Pool Cost Routing

A deployment pool's `routing_strategy` selects its failover logic (shown as "灾备逻辑" in the admin UI): `cost` (成本优先, the default) routes by estimated cost among the pool's members; `load` (性能优先) balances all members by load and live-key weight without looking at price. An empty value (legacy data, or a request that omits it) means `cost`, so every pool without an explicit `load` is cost-priority. There is no data migration: stored values are read back unchanged, and existing pools that explicitly store `load` stay performance-first. The admin pool list has a "灾备逻辑" column (the former description column) showing the strategy label; the description is kept as the pool name's hover title and in the edit modal, which has a "灾备逻辑" select with a short explanation of both logics (default cost-priority). The options and their labels are published through `/admin/data/schema` as `pool_routing_strategies` (default `defaults.pool_routing_strategy = "cost"`; the frontend hard-codes neither), and `POST /admin/data/pools` and `PUT /admin/data/pools/{name}` accept `routing_strategy` and reject unknown values with 400. Strategy changes are hot-published through the normal admin commit pipeline, and pricing template edits take effect through the pricing cache.

Availability always comes first: pause, permission, model and path filters, breaker cooldown, the hard `max_concurrency` capacity and half-open probes all run before price, and price only narrows the already-admitted candidates and never removes the last available option, so price never makes a request fail. Each candidate's cost is estimated from the member's own pricing template at the request instant (`RateFor` with the target, upstream model and current time, so schedule periods and date exceptions such as weekday peak hours and statutory holidays are pure configuration; no vendor, hour or holiday is hard-coded), applied to a fixed reference mix of 1,000,000 uncached input, 1,000,000 cache-read input and 200,000 output tokens, so cache-read price differences matter. Priced members of a cost pool rank first, then cost-pool members with no price for that model, then candidates outside any cost pool (overflow only). Members within 5% of the cheapest estimate form one tier, and inside the tier the existing normalized-load and live-key weighted round-robin applies. Routing falls back to plain load balancing when the pricing source is unavailable or errors. Otherwise tiers are walked from cheapest to most expensive and the first tier with a member below the soft load cap (normalized load of 0.8, the same cap as affinity) serves the request: with A=B < C=D < E, A and B share load and back each other up; only when both are unavailable (cooling, already attempted, at hard capacity) or saturated does traffic overflow to C/D, and only then to E. If every tier is saturated, all admitted candidates share load again. Members without `max_concurrency` never count as saturated, so set `max_concurrency` (for example an upstream's concurrency limit) on cost-pool members for overflow to work. A pool whose strategy is explicitly `load` does none of this.

Upgrade note: after upgrading, pools with an empty `routing_strategy` are scheduled as cost-first (previously they were load-balanced). Members of a cost-first pool should set `max_concurrency`: the soft cap (load 0.8) that spills traffic to the next price tier never triggers for an unlimited member, so traffic concentrates on the cheapest member and only spills over after an upstream 429 or failure cooldown. The admin UI shows a non-blocking notice on pool rows and next to the target editor's max-concurrency field, the pool list response carries the read-only fields `effective_routing_strategy`, `member_capacity_advised` and `members_without_capacity`, and a Warn log (`pool`, `members`, `count`) is written at startup and after a config commit or reload.

For example, a pool holding an official `deepseek-pro` target with a weekday peak/idle schedule template and an aggregator target with a flat half-price template sends peak-hour requests to the aggregator, while idle hours go to whichever is cheaper including the cache price. When the price period changes, in-flight requests, streams and WebSocket sessions are never cut or migrated; only the next request is routed by the new ranking. No strategy actively interrupts a client's stickiness: as long as the sticky target (IP affinity or session binding) can take the request (present, not paused, not cooling, path-compatible, with capacity), it keeps serving it even when a cheaper tier exists. Cost tiers only decide requests with no stickiness, or a temporary re-selection when the sticky target cannot take the new request; that failover does not migrate or overwrite the original binding (IP affinity is not updated on failover, and a session binding changes only on permanent configuration changes), and the client returns to the sticky target automatically once it recovers. Retry and failover limits, historical billing (events are still priced by their own time and serving target), quota, the model-group `cost_coefficient` (not used for routing) and the no-protocol-conversion rule are unchanged. This describes the proxy's routing behavior and has not been verified against real upstream APIs.

The comparison unit is the model name in the client request (the client alias), not each member's upstream model name. A cost-pool member takes part when that request name resolves through the member's own `model_mappings`: it matches the member's `upstream` name or any comma-separated `fallback` alias, and paused mappings are excluded; a member without `model_mappings` accepts any request name and resolves and prices it as-is. Each member still resolves the request name to its own upstream model name (preserving configured case) and then calls the same `pricing.Resolver.RateFor` with `(target, upstream name, selection instant)`. The upstream name sent to the provider keeps its configured spelling, and `model_prefix` applies only to the outbound wire model; the usage event's model is the lower-cased upstream name, and pricing templates bind to the upstream name (not the alias); different members can therefore map the same client alias to completely different upstream names, including case-only differences, and still be compared together.

When a client requests an upstream name directly, the proxy does not reverse-resolve it into aliases or widen the candidate set; only members that resolve that request name take part. The name space is shared across members and many-to-many: one string may be one member's upstream name and another member's alias, and one upstream name may have several aliases. Expanding an upstream name into alias candidates would silently switch the request to a model the client did not name. Unit tests and an e2e counter-example guard this rule. For the same reason, there is no runtime fallback that prices by alias: usage events do not store alias identity, so selecting by alias price would diverge from the billing price recorded under the upstream name; a pricing template's model must be the member's configured upstream model name (the pricing key); the wire model sent to the provider may additionally carry `model_prefix`, which is not part of the pricing key. To express "one price per alias", expand it in the admin UI into per-member `(target, upstream)` bindings (existing templates support multiple bindings) rather than adding an alias pricing key.

The selection price is a directional estimate: it multiplies the fixed reference token mix (1,000,000 uncached input, 1,000,000 cache-read input, 200,000 output) by the template's time-tier unit prices at request entry and ignores request-conditional pricing. Selection and billing use the same `(target, upstream name)` pricing key and the same `RateFor` / `Resolver` entry point, so their unit-price basis is the same; billing, however, uses the actual tokens, the event time, and `ResolveEventRate`, applies `conditions` (input length, service tier, speed), and the model-group `cost_coefficient` further affects the actual bill and quota conversion. The selection price is therefore only a directional estimate and is not equal to the event bill; the final cost is what the event read-back reports. This change does not modify the billing formula, event identity, or price-selection entry point: events are still priced by the actual target, upstream model, and event time. Note the existing repository behavior: directly editing a pricing template inside an effective window reprices that window's history; to preserve a historical basis, add a new template that takes effect in the future.

In the admin UI, the target editor, target list, and target details keep the upstream-first `upstream (alias)` order; the existing "upstream name on the left, client alias on the right" order is unchanged. Only the runtime view of a deployment pool whose effective strategy is cost (`routing_strategy` empty or `cost`) becomes alias-first: member chip hover text shows `alias（上游 upstream）`, comma-separated fallbacks are split into separate labels, paused mappings are marked `已暂停` (paused), and a paused target additionally carries `目标已暂停` (target paused); below the member cell, a visible badge groups members by every client-requestable name declared through `model_mappings`, as `request name · member1、member2`: fallback alias groups come first, client-requestable upstream names appear as secondary groups, members sharing the same request name are merged, the badge's native title carries the secondary information `上游：member → upstream name`, and a paused pool shows no such groups; members without `model_mappings` accept any request name, do not enter a specific group, and are marked `模型 不限` (models: any) only in the member chip. Pools that explicitly store `load` keep the previous chips-only runtime view. The admin UI now provides a read-only cost preview by client request name (button, detail row, and API), described below.

The admin UI exposes a read-only cost preview: `GET /admin/data/pools/{name}/cost-routing?model=<client request name>`. It goes through the existing admin session middleware and sits in the read-only route group, so read-only role sessions can access it; it writes no audit entry, acquires no probes, does not read or modify affinity, and does not change later selection. A blank `model` returns 400; an unknown pool returns 404; a pool whose effective strategy is not cost (an empty value counts as `cost`, so only an explicit `load`) returns 200 with `active:false` and only `pool`, `routing_strategy`, `active`, and `paused`, without preview fields such as `model`, `members`, `reference_tokens`, and `tolerance`. A cost-pool response has the same four outer fields; its cost snapshot fields are `model`, `generated_at`, `pricing_available`, `pricing_error`, `tolerance` (0.05), `reference_tokens` (`input:1000000`, `cached_input:1000000`, `output:200000`), and `members[]`. Member fields include `target`, `upstream`, `resolved_via` (`alias` / `upstream` / `unrestricted` / `none`), `eligible`, `paused`, `priced`, `estimated_cost_usd` (`null` when unpriced), `tier` (0 for the cheapest tier, 1 for a more expensive tier; `null` when unpriced or ineligible), `cheapest`, `reason` (`target_paused` / `mapping_paused` / `alias_not_declared` / `unpriced` / `pricing_unavailable`), `phase`, `in_flight`, `max_concurrency`, and `affinity_soft_cap_reached`. While the pool has at least one eligible priced member, `members` are returned in this order: eligible and priced (tier 0 before tier 1, then by ascending estimated cost), eligible but unpriced, then ineligible (`target_paused` / `mapping_paused` / `alias_not_declared`); ties within a group are ordered by `target` name.

The preview reuses the same `rateSource`, `RateFor(target, member upstream name, now)`, 5% tier tolerance, and fixed reference token mix as selection, so its ranking basis cannot drift; it does not apply the model-group `cost_coefficient` and does not include request-conditional prices (`conditions`) or actual tokens, so it is a routing estimate, not a bill. Actual selection is still affected by availability, capacity, probes, and affinity, and the final cost is what the event read-back reports. When the pricing source is not configured or the resolver is nil, `pricing_available:false` and `pricing_error` carries the corresponding static reason; when resolving the pricing source errors, `pricing_available` is also false, but `pricing_error` only carries the generic reason `pricing source unavailable` and the raw error is written only to the server log. Members are still returned; resolvable members are `eligible:true` but `priced:false`, `tier:null`, `reason:pricing_unavailable`. The admin page shows a read-only-visible cost preview button only on cost-pool rows and expands it as a detail row (not a modal, and with no polling): enter a client request name (the datalist suggests configured names, including names declared by paused targets/mappings so the preview can show why they do not take part; visible group badges still include only enabled members; fallback aliases come first and directly requestable upstream names second, each sorted by name; members without mappings accept any name typed directly). The result table lists member, upstream (secondary, marked alias/upstream name/unrestricted), estimated cost (USD), tier, and runtime state/reason (in-flight/capacity when `max_concurrency>0`, and a soft-cap marker when the affinity soft cap is reached), along with the request name, generation time, reference mix, and tier tolerance returned by the API (the frontend does not hard-code the reference mix), and a note that estimates follow the routing basis (fixed reference token mix) and exclude conditional prices, the model-group coefficient, and actual tokens; actual selection is also affected by availability, capacity, probes, and affinity, and billing is read back from events. The frontend only renders API fields and does not recompute prices in JS; `loadPools` refreshes collapse the detail row, and stale responses are dropped by a sequence guard.

For diagnosis, enable Debug level to see the `cost routing candidates` log. Fields include the alias, admitted/tier counts and `target→upstream[$cost|unpriced|outside]`; the logs contain no secrets or request bodies and are not emitted at the default level. On the IP affinity Set side the proxy still stores the original upstream spelling of the member that served the request; the Get side now tries each upstream spelling that the request name resolves to on each member instead of only the first one in target order, so stickiness no longer silently misses when one alias maps to different upstream spellings. The fix applies to all pools and corrects an existing affinity-identity bug; it does not change `load`/`cost` routing strategy or availability rules. The final selection is still decided by availability, capacity, probes, stickiness, and load.

### Date Exceptions and Request-Conditional Pricing

The effective window for model pricing is still selected by event time; date exceptions and conditional prices are optional template fields. When they are not configured, the original pricing behavior is kept, and no rules are added to existing targets automatically. All costs continue to be computed via `usage.CostRates.CostFor`, and the model group multiplier is applied only once.

- `date_exceptions` apply to time-of-day templates: each entry's `start_date` / `end_date` is a calendar date in the template's timezone, and the range is half-open (start inclusive, end exclusive). For example, to cover October 1–7, enter `2026-10-01` to `2026-10-08`. The template's effective window is selected first, then one set of rates is taken in the order "date exception → weekday time slot → base price"; date exceptions must not overlap.
- `conditions` can be configured separately on the base price, on each weekday time slot, and on each date exception. The time range is selected first, then conditions are matched within that range; conditions in the three scopes do not inherit from each other. The input lower bound `min_input_tokens` is inclusive and the next upper bound `max_input_tokens` is exclusive; `service_tier` and `speed` are independent dimensions. Each condition needs a unique ID, conditions within the same scope must not overlap, and a blank dimension means any value. A match replaces the entire `rates` set; multiple rules or multipliers are not multiplied together. Optional cache/image prices still keep the distinction between a missing value falling back and an explicit 0.
- "More than 272,000 input tokens" corresponds to a lower bound of `272001`, and the higher tier applies to the whole request. OpenAI Chat/Responses use the upstream's raw total input (which already includes cache); Claude uses regular input + cache read + cache write, without additionally stacking sub-items such as TTL, images, and thinking. Missing, conflicting, or overflowing input must not be treated as a known 0.
- The service tier is determined by the actual value in the response. OpenAI `default` is normalized to `standard`, and `priority` in applicable protocols is normalized to `fast`; Claude's `usage.speed` and `service_tier` are recorded separately. Request fields are kept only as evidence and do not determine the actual price. Later omissions in SSE do not erase fields already observed, and an explicit new value updates the old one; WS likewise records per response turn. Allowed values are delivered by `/admin/data/schema` from the domain declarations.
- A pricing context is required only for scopes that have the corresponding condition dimensions configured. When the actual tier is missing, the total input is invalid, or a non-standard combination is not configured, the base estimate for that time range is kept and marked with `cost_incomplete` and diagnostics; forwarding is not rejected and the accounting record is not dropped. Ordinary targets without conditions keep the original behavior. When the tier is known to be standard and no condition matches, the base price is used.

Usage events store `pricing_context` and the selected `pricing_rule_id` / `pricing_rule_version`. The context includes the version, presence/validity of the total input, and the raw request and response tiers along with their observation state; absent, null, empty string, unknown, and valid values are distinguished. The template `version` is a non-negative version number filled in by the maintainer, defaulting to 0 for old templates; the ID/version is price-selection evidence, not an immutable historical billing snapshot. Modifying an old template or deleting an old price still affects recalculation; to preserve a historical basis, add a new template that takes effect in the future and keep the old records. Merely changing the version number does not justify claiming that history is fixed.

Conditional prices are computed per event; long and short requests or different tiers within the same hour must not be merged before price selection. Report and quota increments, recovery, and calibration share the same price-selection entry point. When the raw events needed for conditional pricing have been trimmed by retention cleanup, historical queries return `ErrUsageHistoryIncomplete`; permanent hourly rollups are not enough to reconstruct request tiers, and an estimate must not be treated as a complete bill. Scopes without conditions and with stable prices for the whole hour can still use permanent rollups. Date boundaries in timezones with non-whole-hour offsets also go through the exact event path.

Date maintenance is controlled explicitly by configuration; there is no built-in vendor detection or automatic annual calendar. When maintaining DeepSeek rules, check the vendor's current rules and official holiday notices, and add the next year's dates before the existing rules expire; a missing exception for a given day falls back to the weekday rule and is not automatically recognized as a holiday. The [DeepSeek pricing rules](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/), checked on 2026-10-14, apply peak pricing Monday to Friday Beijing time, excluding statutory holidays, during 09:00–12:00 and 14:00–18:00; weekends and holidays are off-peak all day, so weekends designated as make-up workdays are not raised to peak pricing. The [2026 State Council notice](https://big5.www.gov.cn/gate/big5/www.gov.cn/zhengce/zhengceku/202511/content_7047091.htm) can be used to configure that year's dates, but it does not establish when the vendor's historical pricing terms first took effect.

The sources for the long-input and service-tier examples were checked on 2026-10-14: [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [OpenAI Fast](https://developers.openai.com/api/docs/guides/fast-mode), [Claude long context](https://platform.claude.com/docs/en/about-claude/pricing#long-context-pricing), and [Claude Fast](https://platform.claude.com/docs/en/build-with-claude/fast-mode). These only support documented models and combinations; multipliers must not be blindly extrapolated by model family, and this does not extend the available protocols or automatically enable paused targets. fakellm regressions represent protocol contract verification and cannot replace acceptance against real non-domestic APIs. Shipping this capability does not modify production price tables, fabricate tiers for old events, or automatically recalculate historical costs.

### Home Page Live Activity

The home page shows site-wide and per-client current in-flight requests, the number of clients currently making requests, connected Responses WebSocket sessions, and the input and output tokens recorded in the last five minutes. HTTP/SSE is counted from when an authenticated request with a valid path enters until processing ends; WebSocket is counted per valid `response.create` turn. An idle but unclosed WebSocket counts only toward sessions, not toward the number of clients currently making requests. None of these represent the number of HTTP keep-alive TCP connections.

The read-only interface `/admin/api/activity` is accessed through the existing admin session. Usage is read exactly by event time over `[now - 5m, now)`; site-wide, per-client, and ten-second time buckets come from the same read transaction, with no truncation on event count. The input total includes non-cached input, cache read, cache write, and separate tool input; output directly uses the existing total output, without re-adding subsets such as reasoning, images, and cache durations. Usage for in-progress requests that has not yet been reported is not estimated, and incomplete usage keeps the known numbers with a separate notice. Deleted clients with recent activity or usage remain in the breakdown.

The concurrency chart records the peak for every ten seconds; the server advances the history at request start, request end, and when reading a snapshot, so collection does not require the browser to be open. The site-wide peak is recorded independently and cannot be obtained by summing each client's own peak. Unknown peaks from before the process started, history gaps, and the oldest trimmed bucket are returned as `null`; the current unfinished bucket is marked as partially sampled. A process restart or a wall-clock rollback restarts history sampling, while current in-flight counts are maintained by the actual request lifecycle. Current in-flight site-wide and per-client values come from the same snapshot; WebSocket sessions, configuration, and usage queries have normal sampling time differences and do not represent a globally linearizable snapshot across sources.

The page refreshes live data every five seconds, pauses when leaving the home page or when the page is hidden, and refreshes immediately on return. Activity and history reads each have a twelve-second timeout; on failure, the last data is kept and the update time and a failure notice are shown. Selecting a client only switches the chart scope, and the site-wide summary continues to be displayed; search, sorting, and keyboard readouts are available. The recent audit log was removed from the home page, while the standalone audit feature remains. The existing 72-hour request completion statistics and historical costs are in the secondary area and follow the basis described below.

### Request Completion Statistics

The total request count and success rate in the admin overview use a separate `request_stats_72h`; they are not the usage event count or service availability. Each HTTP request that enters the proxy Service, and each valid WebSocket `response.create` turn that passes the authentication re-check, is counted once when it ends; key rotation and target switching are not counted separately. Success requires a final 2xx, a complete write-back, and no explicit lifecycle failure; supported SSE also requires a protocol terminal state. Missing usage by itself does not mean the request failed. Failures and cancellations both count toward the total, and the success rate is successes / total; with no samples, the success rate is `null` and the page displays `--`.

Samples exclude authentication/IP rejections before the Service, health/admin/ping, WebSocket upgrades and session control, and invalid or authentication-re-check-rejected messages. The statistics interval is `[from, to)`, where `to` is the start of the current UTC minute and `from = to - 72h`; the current unfinished minute is not counted. `since` is the time the new statistics bucket was first initialized and is not derived from historical usage. Per-minute counts are retained independently for 7 days and cleaned up in bounded batches at startup and every 12 hours, unaffected by the usage retention switch.

In JSON or SSE data frames of OpenAI-compatible requests, when the top-level `error` is a non-empty object containing a valid `message`, `type`, or `code`, it is recorded as a business failure even if the HTTP status is 200; subsequent usage or terminal states do not clear that failure. Reported usage is kept, the HTTP status and response body are passed through unchanged, and this does not add retries, target switching, or key banning. `error:null`, empty objects, and nested errors inside generated content do not trigger this rule. The generic rules do not read OpenRouter `error.metadata` and do not recognize MiniMax `base_resp`; these are read by vendor rules only when the corresponding Patch is explicitly selected.

The explicit options for a target's `usage_adapter` are `standard`, `qwen`, `glm`, `deepseek`, `kimi`, `openrouter`, and `minimax`; they are not inferred from host or model name. OpenRouter and MiniMax only add an error Patch; usage is still parsed by the vendor-native parser for the actual protocol. OpenRouter uses the structured budget source to distinguish temporary rate limiting, quota, and balance, and plain 403 text does not trigger it. MiniMax reads the numeric top-level `base_resp` business code only in non-streaming Chat Completions HTTP 200 JSON; known authentication/quota/rate-limit codes switch to another key directly, while unknown non-zero codes are passed through and recorded as usage failed. When all MiniMax keys are exhausted, failover is allowed; otherwise a mapped error is returned instead of the original 200 body. On the proxy side, 2056 is handled as `quota_exceeded`: when no valid future reset time is configured, it is recorded as `quota_exceeded_api` and requires manual wake-up; when a valid reset time is configured, it recovers under the existing keypool rules (consistent with Kimi). The proxy does not derive the M Plan window on its own. Streaming, non-2xx, Anthropic Messages, and Responses all follow the vendor-native rules, and `base_resp` does not trigger the Patch there. Based on [MiniMax Chat OpenAPI](https://platform.minimaxi.com/docs/api-reference/text-chat-openai) and the [official error code page](https://platform.minimaxi.com/docs/api-reference/errorcode), checked on 2026-10-13; documentation review does not equal real API acceptance. For the complete criteria and out-of-scope items, see the [proxy-layer constraints](internal/proxy/AGENTS.md) (Chinese).

Billing relies solely on the token usage fields officially returned by the upstream; the proxy never estimates, backfills, or replays requests. When a client disconnects or cancels mid-request, the proxy cancels the upstream immediately as usual, with no retry and no replay. If the protocol's official final usage fields have not been received at that point and the upstream request may already have been sent, the proxy records one usage event with 0 tokens and an incomplete status, with diagnosis `client_disconnected_no_usage` (shown in the admin console's billing notes as 「连接断开，未获取到计费字段」, "connection dropped, billing fields not received"); partially observed tokens are not counted either. It also writes a Warn log and increments the counter `usage_client_gone_no_usage`. A cancellation that provably happened before any byte was sent upstream writes no usage event. This rule applies regardless of protocol and transport (HTTP, SSE, WebSocket); as a result, the statistics will be lower than the vendor's official bill for these interrupted requests, which is expected. Interruptions caused by the upstream (errors, dropped streams, timeouts, decoding failures, missing terminal events or missing official final usage) are likewise recorded as 0 tokens, with diagnosis `upstream_interrupted_no_usage` and counter `usage_upstream_interrupted_no_usage`; both counters are visible in `/admin/metrics` and on the overview page. Once official final usage is committed, later non-final or empty tail frames cannot overwrite or recompute tokens, model, components, or pricing context; only lifecycle state and diagnostics may change, and a later valid final snapshot replaces the committed one wholesale. Each client request maps to at most one usage bundle, atomically expanded into a root and any linked supplementary records; only the root counts as a request. Failed attempts that are retried or switched to another target during that request are only logged and counted. Explicit advisor and fallback models declared in an Anthropic request are checked against the same target's quota even on paths that do not produce a generation response, such as `/v1/messages/count_tokens`; a request that declares no supplementary model gets no extra check.

For Anthropic final replacements, iteration counters, sums, and model attribution must also be verifiable. Once non-empty iterations have been observed, a replacement with missing, null, or non-array iterations cannot discard the committed bundle. Explicit `[]` and valid snapshots with incomplete costs, such as server-tool charges, can still replace it. First-final conservative handling is unchanged. An `interrupted_after_final_usage` diagnostic survives later valid replacements; a clean replacement does not create it.

The statistics do not store identities, request bodies, or keys, and do not take part in billing, quota, retries, or health settlement. Write failures are logged, and the overview uses this process's `record_failures` to indicate that samples may be incomplete; there is no recovery journal, so counts are not guaranteed to be complete during write failures or process crashes. Read failures are shown as unavailable and do not fall back to old data. The compatibility fields `success_rate`, `requests_72h`, and `success_72h` still use usage events as samples, and their basis is marked with `legacy_sample_basis: "usage_events"`.

### Response Compression and Usage

Usage observation on HTTP responses supports uncompressed, `gzip`, standard `deflate` (zlib), `zstd`, and `br` (Brotli), used to parse JSON/SSE usage. When the client explicitly specifies `Accept-Encoding`, the response bytes and encoding headers are passed through unchanged; when it is not specified, there is no Range, and the request is not HEAD, the proxy keeps its existing automatic gzip negotiation and transparent single-gzip decompression behavior. All encoding header fields are checked together; multi-valued, unknown, or stacked encodings must not be treated as complete usage just because the first header is recognizable. Compression handling applies to all targets and is not controlled by vendor Patch switches. Observation decoding for `br` and `zstd` shares a global memory budget (512 MiB by default, adjustable in MiB via the environment variable `LLMS_OBSERVATION_DECODE_BUDGET_MB`); when the budget is insufficient, usage for that request is recorded as an observation failure while the forwarded bytes stay unchanged, and `observation_budget` in the admin `/admin/metrics` shows current usage and exhaustion counts. `zstd` limits the decoding window to 8 MiB per [RFC 9659](https://www.rfc-editor.org/rfc/rfc9659.html#section-3); this is not a limit on total response length. When the first frame is a single-segment frame whose declared size is between 8 and 64 MiB, the limit is relaxed to the declared size; above 64 MiB the response is rejected at the frame-header stage. For requests whose usage needs to be observed, `br` is removed from `Accept-Encoding` when forwarding upstream (other encodings and q-values are kept; if `*` is present, `br;q=0` is appended; if nothing remains, it is set to `identity`), so that clients cannot use the br decoding budget to evade billing; if the upstream still returns br, it is observed as usual. `br` is used only for usage and trace observation; the encoding scope for non-2xx error classification, vendor detection, and native WebSocket fallback is unchanged. Unknown encodings, multi-layer encodings, and corrupted responses do not have tokens inferred, and their usage is kept as incomplete.

fakellm can generate JSON/SSE responses encoded as `identity`, `gzip`, `deflate`, and `zstd`, as well as encoding header overrides, truncation, and corruption faults. Each SSE frame flushes the compressed stream synchronously; the control plane and WebSocket upgrades do not apply HTTP body compression. The corresponding local e2e (`make e2e`) checks encoding headers, client decoding, persisted usage, and billing; see the [testing notes](scripts/testing/README.md) (Chinese) for details.

Trace uses the same decoding rules and keeps the existing body length limit; a truncated trace does not mean usage observation was also truncated. Older versions that saved unsupported compressed bytes as UTF-8 text may have corrupted the original data, so exact tokens cannot be recovered or costs backfilled from it. The new support only affects subsequent requests and does not rewrite historical usage.

### Request Member Normalization

If a top-level field that affects routing, permissions, billing, or streaming behavior (such as `model`, `stream`, `service_tier`, `input`, `messages`, `tools`) appears more than once or in case variants, the proxy keeps only the last value with the exact spelling at the entry point and removes the other copies and variants before permission checks, billing, and forwarding; if only variants are present, all of them are removed. JSON, multipart forms, `application/x-www-form-urlencoded` forms, and WebSocket requests are handled the same way, so however the upstream parses the request, it only sees the value the proxy authorized and billed. Requests without such conflicts are forwarded unchanged. `custom_body` may not configure case variants of these fields.

Nested pricing-relevant members follow the same rule: `include_usage` and `include_obfuscation` in `stream_options`, `ttl` in `prompt_cache_options`, `cache_control` (including its inner `type` and `ttl`) at the top level and in `system[*]`, `messages[*]`, `messages[*].content[*]`, and `tools[*]`, as well as `content` of `messages[*]`. Deeper locations (such as content nested inside `tool_result`) are out of the current scope.

The request body type is determined by the exact media type in `Content-Type` (three kinds: JSON, urlencoded, multipart), and model extraction, normalization, and form conversion share the same determination. For a request declared as urlencoded whose body (after leading whitespace is stripped) starts with `{` (for example `curl -d` without `-H`): if the body is valid JSON (without a BOM), it is handled as JSON and forwarded upstream with `Content-Type` changed to `application/json` (charset preserved); invalid or near-JSON bodies (for example containing NaN, trailing commas, or a BOM) return `400 ambiguous_request_body`. Requests declared as multipart that are ambiguous to parse return `400 ambiguous_request_body` and are not forwarded, including when: the body is JSON; `boundary` is empty or has leading/trailing whitespace; there is non-whitespace content before the first delimiter; `boundary` uses escaping, uses the `boundary*` extended parameter, or does not conform to the RFC 2046 character set and length; the body contains a non-conforming delimiter line (one that starts with `--boundary` but is not a valid delimiter or close line, or appears after the close line); a part header in a CRLF form contains a line ending only in LF; the part for a protected field (such as `model`) declares a non-UTF-8 `charset` or carries `Content-Transfer-Encoding`; the `Content-Type` parameters cannot be parsed; or a part's `Content-Disposition` is not exactly one header, cannot be parsed, is not `form-data`, or uses the `name*` extended parameter.

Requests with a non-empty body and multiple `Content-Type` headers likewise return `400 ambiguous_request_body`. The proxy does not decompress request bodies: when the body is non-empty and `Content-Encoding` contains any encoding other than `identity`, it returns `415 unsupported_content_encoding` (with `Accept-Encoding: identity` in the response) and does not forward the request.

### Connection and Persistence Performance

All upstream connections share one Transport with TLS session resumption and HTTP/2 enabled (including a 30-second idle PING to detect dead connections) and an 8-second dial timeout; a timeout during dialing is treated as "not yet sent" and switches to the next target, while parent-request cancellation or timeout is still never retried. Request bodies only receive byte-level top-level rewrites (model name, `include_usage`); everything else is forwarded exactly as the client sent it. Usage is first written to the recovery journal (fsync) and then written to the database in background batches, while quota counters are updated immediately before the response finishes; request-completion statistics are written asynchronously. Admin reports may therefore appear a few milliseconds after a request ends. On shutdown the proxy waits up to 30 seconds to flush queued usage; anything not written in time stays in the recovery journal and is filled in automatically on the next start without double billing.

Upstream non-2xx responses follow one failover policy. With nothing yet written to the client and a cacheable error body (at most 64 KiB), a 4xx (except 408) dequeues the candidate and the next one is selected in the pool's routing order; 401/402/403 follow the account-rejection rules below, and a single-key target's 429 dequeues directly (a multi-key target's 429 first goes through the key pool's same-key retry and key switch and escalates only when every key is exhausted). 5xx/408, responses already committed to the client (SSE headers flushed, WS upgraded, Responses events forwarded), sent-then-timed-out or dropped streams, client cancellation and proxy-local request errors remain terminal and are never replayed; 5xx/408 and sent timeouts may already have been computed or billed upstream. An explicit `X-Proxy-Target` disables cross-target fallback, so only keys may rotate on that target. When the queue is exhausted, the proxy replays the first real 4xx (original headers and body) instead of a synthesized status. Exception: a request held by its sticky binding is not handed a substitute target's 4xx; see the bounded in-proxy wait and sticky retry paragraph below. A dequeued 4xx writes no usage, and the successful candidate still owns the request's single usage bundle.

An upstream 401/402/403 is a rejection of the proxy's own account (client authentication has already been checked locally) and is either confirmed or unconfirmed: a non-moderation 403 with a structured code/type/status, an account-level 402 with a readable body, and a 401 matching a known credential rule are confirmed; a non-JSON 403 or one without code/type (for example a WAF/HTML page), an unrecognized 401, and a 402 whose body cannot be read are unconfirmed. Both fail over to the next candidate. Target cooldown: confirmed rejections take the 401/402/403 class (1 hour by default); an unconfirmed one first cools only for `401_unverified`/`403_unverified` (300 seconds by default) and takes the hour only when it recurs within an hour after the previous unconfirmed cooldown ended with no success in between; concurrent rejections of one incident are only counted and never escalate. A multi-key target first cools the rejected key (`forbidden`/`forbidden_unverified`/`unauthorized` or the existing `invalid_token`/`billing_error`) and switches keys; when a key is still active or only briefly rate limited, only this request moves to the next candidate and the target is not cooled. After the cooldown a half-open probe brings the target back automatically, so it is not a permanent block, and the admin UI can clear it manually. Passed through without a cooldown: a content-moderation 403 (structured code/type `content_filter`, `content_policy_violation` or `moderation_blocked`, or OpenRouter moderation metadata when that Patch is explicitly selected; a body beyond the 4 KiB pre-read is judged on the complete body at dequeue), and any 401/402/403 on the client's own credential (`allow_bearer_passthrough` with an `X-Azure-Authorization` header), which never cools proxy keys, cools the target or crosses candidates. A 401 on the proxy's own key is never returned to the client as 401 (client SDKs would read it as their own key being invalid): the queue-exhausted replay and the all-cooling answer use 503 with the upstream status in `X-Upstream-Status: 401` and the body unchanged; a 401 on the client's own credential and an explicit `X-Proxy-Target` pass-through stay 401. When every candidate is cooling after an account rejection, the client receives 402/403 (401 shown as 503) with a proxy-generated `upstream_rejected` error body (controlled `code`, cooling target and `muted_until`) and `Retry-After`; the upstream body is not replayed, and a mix with full, recovering or ordinarily cooling candidates still returns 503. `/admin/metrics` counts account-rejection cooldowns in `requests.upstream_rejection_muted_total` and `upstream_rejection_muted_by_status`, and `targets_runtime[]` shows the reason in `mute_reason`, `mute_status` and `mute_code`.

Target failure cooldowns are classified by error (`server.failure_cooldown_seconds` overrides any class; a restart is required for changes): confirmed 401/402/403 account rejections default to 3600 seconds and are never doubled, `401_unverified`/`403_unverified` default to 300 seconds; 429, 500 and 529 default to half of `quiet_period_seconds` (30 seconds by default); 408, 502, 503, 504, other 5xx and network errors default to `quiet_period_seconds` (60 seconds by default); a 429/503/529 with `Retry-After` cools for exactly that value (bounded to 1 second–10 minutes, never doubled). A non-account class that fails again after its cooldown expires (a failed half-open probe) doubles per consecutive failure up to 8×; late failures from the same incident during a cooldown are only counted and neither raise the multiplier nor extend the cooldown. Only a successful response clears an account-rejection cooldown; a cooling target's ordinary cooldown is ended only by a reachable answer to its own probe, so a late request-level 4xx never ends a 429 or 5xx cooldown early. When no candidate is admissible and none is merely full or recovering, the earliest-recovering target in an early-probe eligible transient cooldown (not an account rejection, not 429) admits one early probe request every 5 seconds, even if other candidates cool after account rejections or 429; success recovers it, failure neither doubles nor extends the cooldown. Attempts that time out after the request may have been sent are still never retried or replayed; only 3 in a row on the same target within a 10-minute window (no success or upstream answer in between) cool it with the 504 class. The admin "clear cooldown" action also resets the unconfirmed-rejection and timeout streaks and restores that target's keys cooled for a 403, credential or billing reason. `targets_runtime[].mute_reason` values are listed in the schema `target_mute_reasons` (for example `upstream_429`, `upstream_5xx`, `network`).

A 429 cools one (target, upstream model) pair, not the whole target: a subscription or per-model rate limit of one model must not push sessions of the target's other models onto a different channel. The cooldown is keyed by the upstream model as the target forwards it (several aliases of one upstream share it; a target without `model_mappings` uses the lowercase request model name; targets are isolated from each other), uses `Retry-After` exactly or the 429 class base doubled per consecutive 429 of that model (capped at 8×), and is cleared only by a real success of that same model (another model's success, a request-level 4xx or a half-open probe answer does not end it), by the admin "clear cooldown" action or a connection-identity change of the target. When a model cooldown ends, a single request probes the model (half-open) while the others see a probe in flight; the probe's success clears the cooldown, a new 429 cools the model again, any other upstream answer ends the entry (the model is reachable), and a cancel gives the probe back. A target holds at most 32 model cooldowns; a 429 beyond that falls back to the target-level cooldown. Account rejections, network errors, 5xx, 408 and 504 stay target-level. On a multi-key target a generic 429 is recorded per (key, upstream model): the key stays usable for its other models, key selection skips keys limited for the request's model, the bounded same-key retry is unchanged (each key gets at most one same-key retry per request, counted within the request, so another model's success on the key cannot reset it), and once every usable key is limited for the model the target cools for that model like a single-key target. Account-level key failures and every 429 of a GLM-selected target remain key-level. While only models are cooling the target phase stays `ready`; selection, sticky hits and cost tiers treat the target as cooling only for requests whose upstream model is limited (it counts toward the earliest recovery but is never an early-probe candidate), and an explicit `X-Proxy-Target` for a limited model receives 503. `/admin/metrics` `targets_runtime[].model_cooldowns[]` (`model`, `until`, `status`, `reason`; always an array) and the key status `model_limits[]` are read-only, and the admin target list/detail and key cards show the limited models and remaining time; the cost-routing preview marks the member's phase `muted` with `model_cooldown_until` for the previewed alias.

Bounded in-proxy wait and sticky retry. A client bound to a target (session or IP affinity) is best served by it, so a brief outage of the bound target should cost latency rather than an error. When selection fails and nothing has been written to the client, the request waits once inside the proxy (until the earliest recovery plus 0-500 ms jitter, only when that is at most 30 seconds away; at most 64 waiters process-wide, beyond which requests fail fast; the wait is not part of `request_timeout`, holds no target slot, key, probe lease or admission token, a client cancel ends it as 499 and a parent deadline as 504, both with no upstream request) and then selects again; a request held by its sticky target first tries that target alone. A wait happens when every blocker is transient (a model-level 429 cooldown, a non-account breaker cooldown), no 4xx has been cached and no 429 was answered, or when the request is held by a cooling or probing sticky target that has not been sent this request yet. A full target is never waited for, and every target is sent a request at most once. Whenever a probe (target or model level) is in flight, with or without an earlier wait, the request polls up to 3 seconds for it to settle (for a request that never waited, the poll is its one wait). A request that used to get an immediate 503 may therefore be delayed by up to about 30.5 seconds (plus the probe polling); the edge proxy's read timeout must stay above that. If the request still cannot be served and it is held by its sticky target (the first selection round hit a session or IP binding whose target is still a legal candidate, no bound target answered this request with a 4xx, is not cooling after an account rejection, and is cooling, probing, full or failed before sending, with a known recovery within 10 minutes for a session binding or 120 seconds for an IP binding), the client receives `503` with `Retry-After` (seconds, rounded up, at least 1; 1 for a full target or a probe in flight) (the sooner of the sticky target's and the other candidates' recovery) and a proxy-generated `upstream_temporarily_unavailable` error body instead of the substitute's 4xx or any other rejection body. When a substitute answered, the response also carries `X-Upstream-Status` and `error.substitute_error_code` (the substitute's error code or type, for diagnosis only; the target is not named). It is counted in `sticky_retry_hinted_total` (and `dequeue_exhausted_total` when a substitute answered), not in `cached_error_replayed_total`, and the binding stays, so the client returns to its target when it recovers. A sticky target's own 4xx (429 included) is still replayed as is, and replaces any substitute's cached answer as a whole. Unchanged: the first real 4xx of an unbound request, deterministic request errors, moderation 403s, client-credential 401/403, explicit targets, 5xx/408, post-send timeouts, committed responses, local quota/parameter/415/499 answers, and a sticky target that cools after an account rejection (its substitute's answer is replayed as before). Every 503 caused by cooldown, full capacity or recovery also carries `Retry-After`; for a native WS turn the error event carries `retry_after`. `/admin/metrics` `requests` adds `in_proxy_wait_total`, `in_proxy_wait_success_total`, `in_proxy_wait_rejected_total` (no slot), `in_proxy_waiting` (current waiters) and `sticky_retry_hinted_total`. The wait applies to every client request, including native WS turns; it never resends a request that reached an upstream.

Affinity is kept only for a response delivered in full (an upstream 2xx whose body reached the client without a write error; a client that closes the connection right after reading the whole response still counts, a client that leaves mid-response does not). A plain 2xx response writes its bindings before the response headers are committed, so a client that sends its next request the moment it has read this one (a new connection per request, no gap) already finds them; if the response then is not delivered in full the bindings are rolled back (the previous binding is restored, but only while the key still holds what this request wrote; a binding another request rewrote is left alone). A failed response, a failover within the same request (even when the first pick was an IP-affinity hit) and probe requests never create or move an IP or session binding, and a hit only refreshes a live sliding binding. In a cost-first pool, a new binding created on a more expensive tier because the cheap tier was down or saturated (including an unpriced member or a target outside the pool while a priced member is eligible) is temporary: 10 minutes for a session and 5 minutes for IP affinity, absolute and non-sliding, never renewed by in-flight requests; afterwards the client re-selects and returns to the cheap tier. An existing sliding binding is never demoted.

### Responses WebSocket

OpenAI targets can enable "Prefer WebSocket for Responses" (「Responses 优先使用 WebSocket」) on the admin page, corresponding to the target field `prefer_websocket`, which is off by default. This switch only affects the upstream transport of synchronous `POST /v1/responses`; Chat Completions and background generation do not use this adapter. HTTP clients can still request SSE or final JSON.

Dual-protocol targets can set `openai_prefix`, `anthropic_prefix`, and `supports_responses` on the admin page. When creating a new canonical `dual_protocol` target, both prefixes default to empty and Responses is off by default; fill them in according to the upstream documentation, as they are not inferred automatically from billing type, domain, or model. Prefixes and the endpoint path share one version rule: when the last segment of the effective base (the prefix, or the endpoint path when the prefix is empty) is a version segment (`/v1`, `/v2`, `/v1beta`, etc.), the client path's leading version segment is replaced to avoid stacking `/v2/v1/...`; a prefix without a trailing version segment is concatenated unchanged. Editing keeps the saved values; clearing a prefix or unchecking the box and saving clears the setting. Switching to another type only hides these three fields and does not clear their values; the compatibility normalization of legacy `bailian` / `bailian_api` configurations is unchanged. The "Test" (「测试」) action on a model row sends a minimal HTTP request to check the upstream response; success only means the HTTP check passed and does not verify the WebSocket channel.

Targets that support OpenAI Chat requests can explicitly enable "Request streaming usage (fill missing only)" (「请求流式用量（仅补缺失值）」), corresponding to the target field `request_stream_usage_if_missing`, which is off by default and is not enabled automatically for existing targets. Only when the actual request path is `chat/completions` and `stream` is the boolean `true` is a missing `stream_options.include_usage=true` added. An existing `true` / `false` or an unexpected type (including `null`) is kept; other nested members are unchanged. Responses, Anthropic, native Gemini, image, and non-streaming requests are unaffected. The order of execution is sanitization or multipart conversion → top-level `custom_body` replacement → model rewrite → fill missing value; explicit `custom_body` configuration takes precedence, and the automatic policy does not correct existing values in it. When switching targets, the request is reassembled from the client's original request and does not inherit the previous target's filled value. If the upstream still returns no usage, `incomplete` / `missing_usage` is recorded and tokens are not estimated. An admin API update that omits this field keeps the original value, and an explicit `false` turns it off; switching the target type only hides the control and does not clear the saved switch value.

The official OpenAI SDK can also connect to the proxy's `/v1/responses` over native WS, authenticating with a proxy client key. Point the SDK's `baseURL` at the proxy's `/v1` address. The native entry point keeps the existing Codex WS path, is unaffected by the HTTP transport switch above, and supports sequential `response.create` for `openai` and `dual_protocol` targets. Each generation still checks client permissions, target admission, and quota, and records usage; named `stream_id`, parallel generation, and Realtime events are not supported.

Connections are isolated per client, and native downstream connections have an additional, independent session boundary. The proxy does not automatically add `previous_response_id` and does not modify `store`. An identity change on a native connection returns `409` (error code `websocket_session_changed`), requiring the client to rebuild the session with the full history; for HTTP clients, upstream WS continuation is only allowed for the latest response cached on that client's still-alive connection, and `previous_response_not_found` is returned when it is unavailable. With the switch off, HTTP upstream continuation still depends on whether the upstream stored that response.

WS preference for HTTP requests and native WS are allowed to fall back to upstream HTTP only when the handshake returns `400/404/405/426/501`, no generation event has been attempted yet, and the context is still valid; native clients still receive WS events, and HTTP business error statuses and error codes are preserved. Authentication, permission, rate-limit, cancellation, and request-timeout errors do not trigger this fallback. If the upstream WS handshake for an HTTP request is rejected with a 429/quota/credential-type error (before any generation event is sent), it retries or switches to another key within the current request under the key pool rules for ordinary HTTP responses; a pre-generation handshake rejection on native WS can likewise switch to another key within the current turn under the same rules. Uncertain send results, stream interruptions, or terminal failures never replay the generation, and terminal key feedback after generation only affects the next turn. Missing usage is marked as incomplete and not treated as a zero-cost success. After a handshake is rejected with `404/405/426/501`, new connections with the same handshake identity (URL and forwarded headers, including upstream credentials) go directly over HTTP for 10 minutes, while existing connections and their continuations are unaffected; `400` may come from a single client's request headers and is not remembered; a configuration update clears this record. The upstream WS pool for HTTP requests retires connections after 5 minutes idle or once the connection reaches 55 minutes of age; idle connections are pinged periodically and retired if unresponsive; when the pool is at capacity, the current request uses HTTP instead (before any generation event is sent). After a request finishes, the proxy pre-dials one unused spare connection for the same client in the background (at most one per client) so the next new request can use it directly and skip a handshake; a failed background dial does not affect key, circuit-breaker, or fallback records. Native WebSocket sessions send a ping when the upstream has been idle for 30 seconds between turns, so that the connection has not already been closed by the upstream when the session continues. Request and event JSON is forwarded as the original bytes, adding or removing only the necessary top-level members. New requests without `previous_response_id` prefer a new connection, to avoid overwriting the continuation point of the same client's other sessions. A configuration update clears the unsupported and background-dial backoff records, cancels spare dials in progress, and retires idle pool connections that hold no response. Connections of a deleted target, or opened with a key removed from its target, are retired too, including ones holding a response: idle ones close immediately and ones in use close when their request finishes, rather than staying connected until the idle timeout. Other connections holding a cached response and connections in use are kept, because a connection is only reused by requests with the same URL and authentication headers, so saving an unrelated target no longer breaks HTTP continuations. A connection opened before the update never pre-dials a spare afterwards, since its key may have been removed by the save; if released without a response it is retired. Manually blocking a key retires every pool connection opened with that key, including ones holding a response.

WS and HTTP are only different transports and share the same retry, failover, key cooldown, circuit-breaker, and concurrency (AIMD) rules. An upstream WS upgrade handshake that times out before any upgrade response, while the request is still alive, has sent no `response.create`: like an HTTP dial timeout it fails over to another target once and counts as a target failure, and it never falls back to HTTP on the same target; with no other target, an HTTP request receives `503` as for an HTTP dial timeout. Client cancellation and the request timeout are never retried. A failed native turn ends with one `{"type":"error","status":N,"error":{...}}` event. Proxy-local JSON rejections (for example quota `quota_exceeded` with `error.quota.resets_at`, `quota_not_configured` (403, no `resets_at`), `accounting_unavailable`, `upstream_rate_limited`, `upstream_quota_exhausted`) pass their `error` object through unchanged, and when the equivalent HTTP response carries `Retry-After` the event additionally has `retry_after` (seconds); existing fields are unchanged. Proxy error codes include `websocket_session_changed` (409), `upstream_invalid_event` and `upstream_event_too_large` (502, an upstream event in the HTTP fallback could not be forwarded; the turn ends, the session stays usable, nothing is replayed), `upstream_disconnected` (502), and `upstream_timeout` (504). Client messages do not include upstream URLs; an upstream close code is recorded only in the diagnostic log (`upstream_close_code`).

Native downstream connections are closed with 1000 after 15 minutes idle between turns, and the server sends a ping every 30 seconds; each client credential allows at most 64 concurrent native sessions, and exceeding that returns `429`. While a turn is in progress, a session from which neither a pong nor any frame has arrived for max(4 × ping interval, 2 minutes) is treated as half-open: the server sends a 1001 close frame ("client unresponsive") and ends the session, releasing its session slot. Between turns this check does not apply, because many WebSocket client libraries answer pings only while the application is reading; a quiet client there is governed only by the 15-minute idle rule. There is no fixed read deadline. For the idle (1000) and shutdown (1001) closes, the server waits up to 1 second for the client's close frame before closing TCP. On service shutdown, in-progress generations are first allowed to complete and be accounted for within the shutdown grace period, then sessions are closed with 1001; generations that exceed the grace period are canceled and recorded as incomplete usage. Native clients must handle disconnects and explicitly decide how to reconnect and continue.

## Codex Ultrafast WebSocket Example

Codex can use Responses WebSocket through LLMs Proxy → CLIProxyAPI → the Codex OAuth upstream. This setup requires CLIProxyAPI to have a working Codex OAuth account configured, with `websockets=true` in that account's auth metadata/attributes. The three layers of credentials serve different purposes: Codex's `env_key` uses the LLMs Proxy key assigned to the Codex client; the LLMs Proxy target's `APIKey` uses CLIProxyAPI's own API key; CLIProxyAPI holds the Codex OAuth login credentials and the corresponding account entitlements.

In the LLMs Proxy target configuration, select the target that corresponds to CLIProxyAPI, set the endpoint type to `openai` or `dual_protocol` (Responses WebSocket currently supports only these two; do not choose `azure_openai`), and enter CLIProxyAPI's endpoint and API key. In `CustomBody`, add the key `service_tier` with the value set to the string `ultrafast` (written as `"ultrafast"` in JSON). In the model row on the web page, the left side is the upstream name, `gpt-6.1-sol`; the right side is the client alias, `codex-sol-ultrafast`. This maps the client's generic alias to the upstream model name, and the upstream model name keeps its original spelling. If your Codex version has no model metadata for this custom alias, you also need to provide a matching Codex model catalog entry. Target and mapping changes on the web page take effect only after they are saved.

Example Codex `~/.codex/config.toml`:

```toml
model = "codex-sol-ultrafast"
model_provider = "llms-proxy"
service_tier = "ultrafast"

[model_providers.llms-proxy]
name = "LLMs Proxy"
base_url = "https://proxy.example.com/v1"
wire_api = "responses"
supports_websockets = true
env_key = "LLMS_PROXY_API_KEY"
requires_openai_auth = false
```

The process that launches Codex needs to obtain the `LLMS_PROXY_API_KEY` environment variable from a secure credential source. `env_key` is the credential the Codex client uses to connect to LLMs Proxy; do not copy the key into TOML, command arguments, logs, or Git commits. Do not set `requires_openai_auth` to `true`: with that setting, Codex ignores `env_key`. `supports_websockets` declares that the provider supports Responses WebSocket; `base_url` together with `wire_api = "responses"` makes Codex use `/v1/responses`, and the WebSocket address is `wss://proxy.example.com/v1/responses`.

This integration covers ordinary Codex Responses WebSocket sessions: the client sends flat `response.create` events, can warm up with `generate = false`, and continues turns sequentially via `previous_response_id`. Every new event re-validates the client key, ACL, IP restrictions, and target admission, and uses the same usage recording as ordinary requests. It does not imply support for parallel `stream_id`, mid-stream steering, or `response.append`. If the target, URL, or authentication identity changes on a connection that already has a `previous_response_id`, the service returns `409`; the client should reconnect with the full history, and the proxy will not silently switch upstreams and replay.

Configuration only expresses a request preference; it cannot prove that the upstream actually used Ultrafast. During acceptance, separately verify that the outgoing request contains `service_tier: "ultrafast"` and the actual tier read back from the upstream response's `response.service_tier`; also confirm that the Codex OAuth account selected by CLIProxyAPI meets the plan eligibility. OpenAI currently limits Ultrafast to certain advanced models; refer to OpenAI's current official support list for which ones; Pro $500 included usage is counted at 8× Standard, after which available credits are used, and purchased credits are counted at 6× Standard. See the [Codex Speed guide](https://learn.chatgpt.com/docs/agent-configuration/speed), [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), [Codex Gateway compatibility requirements](https://learn.chatgpt.com/docs/enterprise/gateway-compatibility), [Responses WebSocket guide](https://developers.openai.com/api/docs/guides/websocket-mode), [CLIProxyAPI Codex client configuration](https://github.com/router-for-me/CLIProxyAPIDocs/blob/main/docs/en/agent-client/codex.md), [CLIProxyAPI Codex WebSocket configuration sample](https://github.com/router-for-me/CLIProxyAPI/blob/main/config.example.yaml#L583-L626), and [CLIProxyAPI WebSocket auth selection logic](https://github.com/router-for-me/CLIProxyAPI/blob/main/internal/runtime/executor/codex_websockets_executor.go#L123-L140). The configuration examples in this repository and the CLIProxyAPI upstream source do not mean that the version you deployed supports this capability; after deployment, still read back the actual version and record the requested tier and the actual tier in the response separately.

## Testing

```sh
make test
go vet ./...
go vet -tags=e2e ./test/e2e/
go build ./...
go test -race -count=1 ./internal/proxy/... ./internal/nosql/... ./internal/usage/... ./internal/quota/... ./internal/admin/... ./cmd/proxy/...
make integration
node scripts/testing/admin_ui_test.cjs
(cd internal/admin/ui && node --test)
make e2e
python3 -m unittest scripts.test_verify_azure_v1_models scripts.test_workflow_image_tag
```

`make test` first runs `make check-docs`, then runs `go test ./...`. The docs check requires `AGENTS.md` to exist. This records the project gates and does not mean the tests have been run for this change.

`make e2e` builds the real proxy binary and connects it to the in-process deterministic fake upstream `internal/fakellm`, without calling any real model. For the admin frontend test tooling, see the [testing notes](scripts/testing/README.md).

Upstream API credentials and client access keys are kept only in protected local configuration or environment variables; they are not committed to Git, not passed as command-line arguments, and not printed to logs. Checks that were not run must be explicitly marked as unverified.

## Contributing

- **Specifications live in Issues.** Each independently verifiable goal gets a GitHub Issue (managed with SpecGit) with the Chinese sections 原因 / 范围 / 方案 / 验收 (reason / scope / approach / acceptance); progress, blockers and evidence links are kept there. Issue and Pull Request titles and bodies use Chinese, with exceptions for proper names, commands, code, necessary type prefixes and references. Pull Requests reference the Issue with `Closes #N` or `Refs #N`.
- **Feature branches into `dev`.** Work on a feature branch and open a Pull Request targeting `dev`; do not push directly to `dev` or `main`. Fill in the [PR template](.github/pull_request_template.md): summary and linked Issue, TDD evidence, gates run, unverified scope, and whether billing, protocols or compatibility are affected.
- **`main` is fast-forward only.** After `dev` passes acceptance, `main` is fast-forwarded to the accepted `dev` commit; nothing is committed or merged on `main` separately.
- **Tag last.** A version tag and GitHub Release are created only after both staging acceptance and the production smoke test of the same image have passed, never earlier.
- **TDD for behavior changes.** First add a test that fails for the right reason, then change the implementation and show the same test passing. Behavior-preserving refactors and documentation-only changes need no artificial failure, but must state the checks that were run.
- **Run the gates locally first**, with the Go version declared in `go.mod`, using the same commands as CI.

CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs on pushes to `dev` and `main` and on Pull Requests targeting them, uses only GitHub-hosted runners and no secrets, and cancels superseded runs on the same ref. These job names are the required status checks for `dev` and `main` and are kept stable:

| Job | Command |
|---|---|
| `test` | `make check-docs`, `go vet ./...`, `go vet -tags=e2e ./test/e2e/`, `go build ./...`, `go test ./...`, `make test-fast-integrity`, `make coverage-check` |
| `race` | `go test -race -count=1` over `internal/proxy`, `internal/nosql`, `internal/usage`, `internal/quota`, `internal/admin` and `cmd/proxy` |
| `e2e` | `make e2e` |
| `integration` | `make integration` |
| `admin-ui` | `node scripts/testing/admin_ui_test.cjs`, `(cd internal/admin/ui && node --test)` |
| `scripts` | Python unit tests for the tracked `scripts/**/test_*.py` and `scripts/test_*.py` (`python3 -m unittest`) |

`.github/workflows/docker-build.yml` is an optional, manually run image build and is not a required check; releases attach only the source archives by default.
